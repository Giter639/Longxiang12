# 协作规范（X01 交付物，R1 维护）

## 分支模型

```
main        可安装 APK 的稳定版，只接受 dev 的 PR，永远打 tag
dev         集成分支，每天 D+N 收工前合入并出当日构建
feature/X02-nav   个人工作分支，命名 feature/<任务ID>-<短名>
```

- 每天开工从最新 `dev` 切分支；任务完成 → PR → 至少 1 人 Review → 合入 `dev`。
- `dev` 出现编译失败：合并者 30 分钟内修复或回滚，不许"先合着"。

## 提交与 PR

- commit 格式：`<任务ID>: <做了什么>`，例：`T3-03: 冷却规则改为按类型独立计时`。
- PR 模板见 `.github/PULL_REQUEST_TEMPLATE.md`，**验收标准一栏必须引用任务卡的量化指标**。
- Review 清单（Reviewer 逐条勾）：
  1. 编译通过 + `testDebugUnitTest` 全绿；
  2. 没有绕过 Tracker / AppSessionViewModel / MetricDefs 三条硬规则（见 README）；
  3. 文案没写死在代码里；
  4. 涉及口径的改动，R1+R2 **双方**都在 PR 里回复过"确认"（协议改动已豁免 R1 双签，R4 定稿即可）；
  5. 没有"待办未标注 TODO"的半成品逻辑混入主链路。

## 版本与发版（X06）

- 版本号 `1.0.D<天数>`（如 1.0.D3 = 第 3 天构建），versionCode 每次发版 +1；
- 每天 D9 之前：`dev` → `main`，打 tag `release/D<N>`，出可安装 APK 给 R2 回归；
- 崩溃收敛目标：5 个演示场景连续跑通不崩（X06 验收）。

## 每日节奏（配合任务卡）

- 站会前各自更新任务卡"完成情况"列（未开始/进行中/已完成/阻塞）；阻塞必须当天群里说清卡点与需要谁；
- D6 起 R2 组织 30 分钟回归，只测 5 条主路径；Bug 清单每天更新，不口头传递；
- 口径冻结点 D5、协议冻结点 D3（R4 接口协议 v0 当天定，之后改动走 PR）。

## 数据与隐私红线（全组）

- 不上传任何数据：报告、样本、埋点全部本地 Room（`allowBackup=false`）；
- 不做医学化表述（R2 用词清单为准）；不提供不可解除的锁机。
