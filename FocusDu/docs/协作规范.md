# 协作规范（X01 交付物，R1 维护）

## 分支模型

```text
main        可安装的稳定版本，永远打 release tag
feature/<任务ID>-<短名>    从最新 main 创建的个人工作分支
fix/<任务ID>-<短名>        缺陷修复分支
docs/<任务ID>-<短名>       文档与规范分支
```

- 每次开工前先同步最新 `main`，再从 `main` 创建独立任务分支。
- 一个任务对应一个分支、一个 PR；大改动拆成多个小 PR。
- `dev` 已退出日常开发流程，不再作为新功能或新修复的集成分支。

## 提交与 PR

- commit 格式：`<任务ID>: <做了什么>`，例如 `T3-03: 冷却规则改为按类型独立计时`。
- PR 目标分支固定为 `main`。
- PR 模板见 `.github/PULL_REQUEST_TEMPLATE.md`，**验收标准必须引用任务卡中的量化指标**。
- PR 合入前必须同时满足：
  1. CI `build-test` 通过；
  2. 至少 1 人 Approve；
  3. 由有权限成员手动 Merge。
- 管理员同样受分支保护规则约束，不直接向 `main` 推送业务改动。

Review 清单：

1. 编译与测试通过：
   - `./gradlew :app:assembleDebug`
   - `./gradlew :app:testDebugUnitTest`
2. 没有绕过 Tracker / AppSessionViewModel / MetricDefs 三条硬规则。
3. 面向用户的文案在 `res/values/strings.xml`，代码中没有新增硬编码中文。
4. 涉及指标口径的改动，R1+R2 在同一 PR 中确认。
5. 涉及视觉接口协议的改动，由 R4 定稿。
6. 没有未标注 TODO 的半成品逻辑进入主链路。

## 版本与发版（X06）

- 版本号 `1.0.D<天数>`，例如 `1.0.D5`；versionCode 每次发版递增。
- 版本从 `main` 构建并打 tag，例如 `release/D<N>`。
- 每天完成约定功能、CI 和审批后，从 `main` 产出可安装 APK 给 R2 回归。
- 崩溃收敛目标：5 个演示场景连续跑通不崩溃。

## 每日节奏

- 开工前同步最新 `main`，确认任务卡状态、验收标准和依赖。
- 站会前更新对应任务的完成情况：未开始 / 进行中 / 已完成 / 阻塞。
- 阻塞任务必须说明卡点、需要谁处理，以及解除条件。
- D6 起 R2 组织每日主路径回归，Bug 清单需要持续更新。
- 口径在 D5 前定稿；视觉接口协议由 R4 定稿。后续修改均走正常 PR。

## 数据与隐私红线

- 不上传报告、视觉样本、埋点或其他用户数据。
- 原始视频不保存、不上传；通知内容不读取、不持久化。
- 不做医学化表述，不提供不可解除的锁机。
